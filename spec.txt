1. Product Overview
The system is a cloud-hosted MT5 trade-copying platform. A user connects one Master account and zero or more Sub accounts. A trading action on the Master is detected by the Master EA, passed into an asynchronous processing pipeline, evaluated for each Sub account, and executed by the relevant Sub EA when approved.

2. Core Architecture
The platform uses a hybrid architecture. MT5 EAs are responsible for time-sensitive MT5-native event detection and execution. The backend owns business logic, risk decisions, mapping, recovery, security, configuration, and the web API. The dashboard is a control and observability layer, not the authority for trading decisions.

Performance Architecture
The Master EA event handler must remain lightweight. It should not perform large database operations, blocking HTTP calls, or heavy business logic inside the critical event callback. It should capture/normalize the event and hand it off to a local queue or asynchronous worker so the handler can return quickly.

8. SL and TP Handling
Stop Loss requirement
Because the risk engine needs the SL to determine planned monetary exposure, a new Master trade without an SL enters WAITING_FOR_SL. The default waiting period is 60 seconds and is editable in the dashboard.
No SL → WAITING_FOR_SL
SL arrives in time → continue
Timer expires → EXPIRED / not copied
SL added after expiry → do not auto-resurrect; optional manual synchronize
Take Profit
TP is optional. If a trade has no TP, the system performs risk validation but does not reject the trade because of RR. If TP is added later and Copy TP is enabled, the modification is synchronized.
9. Pending Orders
Pending orders are first-class objects with their own lifecycle. The system must support the applicable MT5 order types, including Buy Limit, Sell Limit, Buy Stop, Sell Stop, and stop-limit variants where supported by the instrument/broker.

The Risk Engine makes an independent decision for each Sub account. It is the single source of truth for risk calculations. The frontend must never perform authoritative risk decisions.

Target monetary risk
Conceptually: Target Monetary Risk = Account Equity × Risk Percentage. The final volume calculation must use the actual MT5 symbol specifications for the specific Sub environment, including contract size, tick size, tick value, volume limits, volume step and applicable currency-conversion behavior.
12. Smart Lot Rounding and Rounding Tolerance
Each Sub account has an editable Maximum Rounding Difference. This setting exists only to control the small difference caused by broker volume steps. It does not add a fixed percentage to the normal risk setting.
Example
Equity = ₦200,000
Risk = 1%
Target risk = ₦2,000
Rounding difference = 2%
Allowed excess from rounding = ₦40
Maximum acceptable rounded risk = ₦2,040
₦2,025 → allowed
₦2,100 → too high; round down or reject if necessary
The dashboard must explain this setting using clear inline help/tooltip language so users cannot reasonably confuse rounding tolerance with additional risk.
13. Minimum and Maximum Volume Protection
If the exact calculated volume is below the broker minimum, the system evaluates the actual risk of the minimum executable volume. If the minimum volume exceeds the configured risk/risk-rounding limits, the Sub trade is rejected.
If the calculated volume exceeds the broker maximum, the system evaluates the risk at the maximum permitted volume. If the maximum volume still fits the configured risk controls, it may execute at the maximum; otherwise, the Sub trade is rejected.

18. Hedging vs Netting
The system automatically detects the account trading/margin mode and uses mode-aware mapping.
HEDGING
GBPUSD BUY 0.50
GBPUSD BUY 0.30
GBPUSD SELL 0.20
(each is a separate position)
NETTING
Multiple deals may contribute to one net position per symbol.
The copier must never assume one symbol equals one position.
19. Partial Close Behavior
Partial closes are copied proportionally. The system calculates the percentage of the Master position reduced and applies that percentage to each mapped Sub position, then respects the Sub broker volume step and execution constraints.
Master 1.00 → closes 0.40 = 40% reduction
Sub A 0.50 → closes 0.20
Sub B 0.20 → closes 0.08
20. Recovery and Reconciliation
Cloud/VPS interruptions are considered expected failure cases. After reconnection, the system reconciles current Master state against stored mappings and Sub state.

Find current Master orders/positions
  ↓
Compare with mappings
  ↓
Already mapped? → restore synchronization
Not mapped? → recovery validation
  ↓
SL exists?
Trade still exists?
Risk still valid?
RR still acceptable?
Sub executable?
  ↓
RECOVER or REJECT
Already-copied trades do not go through stale-trade recovery; their mappings are restored and synchronization resumes.

Latency telemetry
Measure timestamps across the path: Master event detected → backend received → risk calculation finished → command sent → Sub EA received → broker execution confirmed. The system should report measured latency instead of promising an absolute fixed time.
24. Security Requirements
All privileged authorization decisions happen server-side.
MT5 credentials and secrets are encrypted/protected and never exposed in frontend code.
No credentials or secrets committed to source control.
Use environment variables or managed secrets for runtime secrets.
Isolate each tenant/user data scope at the backend and database layers.
Protect EA-to-backend communication with authenticated instance identities/tokens.
Record security-sensitive actions in audit logs.
Use secure session/token handling and appropriate rate limiting.

30. Definition of Done / Acceptance Criteria
A user can create an account and securely connect Master/Sub MT5 accounts.
The Master EA detects manual Master trading activity from MT5 and forwards normalized events.
The system supports market and supported pending order types.
The system waits for an SL when risk-based copying requires it and expires the trade after the configurable timeout.
Each Sub receives an independent risk calculation based on its own account conditions and symbol specifications.
Minimum/maximum volume and volume-step constraints are enforced.
Rounding tolerance is configurable per account and clearly explained in the UI.
Daily risk and maximum-trade protections can be enabled/disabled per account.
Risk overrides can apply to the next Master trade and can be ignored by individual Sub accounts.
Master/Sub trade mappings persist through restart/reconnect.
SL/TP/modification/partial-close/full-close synchronization works according to per-account copy settings.
Recovery does not blindly copy stale trades and applies the agreed RR/risk validation rules.
The dashboard updates account state, positions and P/L in real time.
The Owner account has server-side Admin access and no subscription requirement.
Normal users cannot elevate themselves to Owner/Admin through the frontend or API.
The codebase is modular, documented, tested and understandable by another developer.
Cloud execution environments can be monitored and recovered.
The system produces actionable logs and pre-execution risk calculation records.
